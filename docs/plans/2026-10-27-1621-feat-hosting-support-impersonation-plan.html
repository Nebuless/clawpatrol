Goal Capsule

Objective. Customers can choose where PRX runs and let an assigned technician inspect their real gateway account for a bounded support session they can end themselves.

Means. One gateway and client registry per customer, an independent Provider control plane, verified technician OIDC/MFA, customer-issued phone codes, and an opt-in outbound dashboard connector.

Authority. Product Requirements own behavior. Key Technical Decisions own mechanisms within those requirements. Units sequence work and do not override either. Existing user-directed decisions remain fixed.

Stop conditions. Stop affected work if a change requires shell access, wider provider privileges, bypassing customer approval, guessing technician MFA assurance, losing WIP, or publishing unrelated branch history. Missing external credentials blocks deployment, not pure local implementation with explicit test fixtures.

Execution profile. Security-sensitive, phased delivery. Main coordinator owns independent plan/code reviews, approved builds, browser checks and shipping. This artifact does not authorize installs, live services, credential provisioning or release tags beyond the parent user's applicable approvals.

Product Contract

Problem Frame

PRX currently authenticates a single password-root dashboard or allowlisted tailnet operator. It has no durable customer organizations, assigned support technicians, dashboard impersonation sessions or Provider control plane. Registry roles already distinguish global advisories from a customer's customized registry, but that does not create customer identity or support authority.

Summary

Add customer hosting registration and narrowly constrained account impersonation. The technician opens the gateway's existing dashboard, not a replicated Provider dashboard or remote terminal. Keep global vulnerability aggregation independent of hosted account management.

Key Decisions

  • Customer-hosted and Nebuless-hosted are equal hosting choices. Existing registered gateways are valid hosted targets. Governs R1, R2. (session-settled: user-directed — chosen over mandatory cloud provisioning: hosting location must not change the registry's client role.)
  • Use account impersonation, not remote shell. Governs R3, R7. (session-settled: user-directed — chosen over shell access: support needs the customer's normal UI and account context.)
  • Customer phone approval precedes actual view-as in both hosting models. Governs R4–R6. (session-settled: user-directed — chosen over silent hosted impersonation: selecting an organization is not permission to become a user.)
  • Keep support, hosted management and advisory authority separate. Governs R8, R11. (session-settled: user-directed — chosen over a shared superuser credential: compromise must not cross those boundaries.)

Actors

  • A1. Customer administrator: authenticates locally, registers the installation, submits a case, approves a target account and can revoke support.
  • A2. Assigned technician: stable named Provider identity, own MFA, explicit organization authorization and case assignment.
  • A3. Provider administrator: registers hosted targets and assigns technicians, but cannot bypass customer approval or use advisory signing authority.
  • A4. Gateway and customized registry: enforce local account scope and keep local security state.

Key Flows

  1. F1. Register an existing customer gateway, choose hosting metadata, enroll its connector, verify its pinned installation identity and registry client role. Covers R1, R2, R11.
  2. F2. Customer submits a case, Provider assigns an authorized technician, customer refreshes verified assignment, chooses an eligible local account and generates a SUPPORT code. Customer reads it only to that named technician. Covers R4, R5.
  3. F3. Technician completes own MFA, opens assigned case, redeems phone code and enters a separate support origin serving that gateway's real dashboard. Covers R3, R5–R9.
  4. F4. Customer or technician ends session, or expiry/disconnection closes it. Next request and pending SSE delivery fail. Customer inspects retained audit locally. Covers R7, R9, R10, R12.

Scope Boundaries

Implement organization/installation registration, local stable dashboard accounts, submitted cases and assignment, OIDC technician authentication, consent codes, dedicated support sessions, outbound connector, Provider selection UI and audit. Do not build billing, cloud account APIs, VM provisioning, general multi-tenant data-plane hosting, remote shell, registry policy redesign or a generic identity platform.

Planning Contract

Current implementation evidence

  • cmd/nebprx/web.go: principal, dashboardAuthGate, tailnetGate, routes and csrfProtect(dashboardAuthGate(tailnetGate(mux))). Route metadata currently classifies authentication, not support capability.
  • cmd/nebprx/dashboard_users.go: only dashboardRootUsername = "root" is used for password login. dashboard_sessions.go stores SHA-256 hashes of random 32-byte session tokens. Tailnet auth is not a revocable dashboard session.
  • selectedProfileForRequest accepts query/header selectors. apiState caches by principal kind/owner/profile. agents.go:statusList and apiRules can expose broad instance state. These are not existing tenant or user isolation mechanisms.
  • apiConfig reads raw HCL. Action exports and live events may contain request bodies. Reusing all authenticated routes unchanged would leak credentials or grant administrative actions.
  • dashboard/src/App.tsx routes by hash. getState caches a module-level ETag/body and App.refresh currently swallows errors. Both need explicit session-boundary handling.
  • Latest migration at inspection: 0024_device_node_id.sql. Existing registry implementation is uncommitted prerequisite WIP, not evidence that hosting/support has shipped.

Assumptions

Each deployed customer instance belongs to exactly one organization. Existing password root and allowlisted tailnet dashboard operators retain their present instance-wide permission ceiling. This release does not invent customer RBAC roles or use a profile query parameter as a user identity. Persist explicit account records and context now so impersonation resolves an actual customer account rather than manufacturing a generic root session.

Key Technical Decisions

KTD1. Separate Provider command and stores

Add nebprx provider for hosted registration, cases, technicians and broker. Keep customer gateway database separate from Provider SQLite and from internal/registry storage. Use one Provider process with its own state directory in this release, not distributed HA. Advisory server remains nebprx registry --mode server. Hosting type is metadata on a registered installation, not a provisioning action. Implements R1, R2, R8, R11.

KTD2. Stable local accounts and explicit dual principal

Add installation/org binding and dashboard_accounts. Generate opaque stable IDs, with unique (auth_kind, auth_authority, auth_subject). Password root binds to its existing username and credential generation. Retain upstream UserProfile.ID in the verified tailnet identity adapter. Tailnet accounts bind to that ID and the persisted local tailnet authority, never mutable login names or caller headers. Refresh current subject eligibility from a server-trusted local tailnet membership source before support admission; a saved login name alone is insufficient. If current membership cannot be proven, deny that target rather than promise immediate removal handling from cached data. Authority changes retire old account bindings and invalidate their support grants/sessions. Root deletion/reset invalidates support; recreating root creates a new account generation and never revives old grants. Preserve the existing root-absence gate for every target. Keep historical names/IDs in audit.

Extend principal with Actor, Effective, OrganizationID, InstallationID, SupportSessionID and Capabilities. Existing Owner remains the effective legacy owner for existing handlers. Never put the technician in Owner. Resolve account rights and feature flags from the local account/current config for both ordinary and support requests. Persist bounded dashboard_context for selected profile, filters and last route, validated against current rights. Support reads a snapshot but cannot overwrite the customer's saved preferences. Implements R3, R7, R9.

KTD3. OIDC authorization code + PKCE and explicit assurance

Use maintained github.com/coreos/go-oidc/v3/oidc (v3.17.0 already recorded in go.sum, verify supported version at implementation) as a narrow direct dependency, with existing golang.org/x/oauth2. Do not implement OIDC validation over generic jose. Configure HTTPS issuer, authorization, token, JWKS and RFC 7662 introspection endpoints. Use the verifier for signed issuer/audience/algorithm/expiry validation, with explicit application checks for nonempty subject, nonce, required azp, allowed acr and recent auth_time. Authorization requests include openid, PKCE S256, max_age and the configured assurance request. A one-use 5-minute server-side state/nonce/PKCE transaction is bound to a host-only login browser cookie; stolen callback parameters in another browser fail. No caller-selected discovery URL or algorithm.

Configure an exact issuer-specific allowlist of MFA-backed acr values after checking IdP policy. Technician roster maps (issuer, sub) to immutable technician ID/name/roles. No email-based enrollment. Require assured authentication within 5 minutes at redemption. Provider session expires at the earliest of access-token expiry and 30 minutes after authentication; no refresh tokens.

Store only hash of Provider cookie and encrypt the IdP access token at rest with a separate owner-only key. On every protected Provider/support request check local session/roster/assignment and authenticated introspection, without a positive cache. Supported introspection profile requires active=true, sub equal to verified ID-token subject, client_id equal to configured OIDC client, future integer exp, and matching iss. Use explicitly configured client_secret_basic with separate introspection client ID/secret; do not assume optional RFC 7662 claims exist. Missing/mismatched claims fail closed with an actionable configuration diagnosis. The IdP must invalidate introspection on user disablement; document and verify that integration requirement rather than claim all issuers do. Gateways accept only Provider-generated envelopes on enrolled channels, never browser actor/MFA headers. Implements R5, R8, R12.

KTD4. Local consent state machine

Customer submits a minimal structured case through its enrolled connector. Provider persists case and assignment revision. Gateway must fetch current assignment before issuing a code and check it again at redemption. Case state is submitted → assigned → closed. Reassignment increments revision and invalidates associated local grants/sessions. A closed case cannot reopen an old grant.

Generate SUPPORT-XXXX-XXXX-XXXX with 12 uniformly sampled Crockford Base32 characters (60 bits). Accept case-insensitive ASCII plus displayed separators only. Lifetime 5 minutes, single use, fixed 15-minute session ceiling, no refresh. Display raw code once, memory only; store HMAC-SHA-256 using a distinct owner-only local pepper with grant/installation binding. A reissue revokes previous active code for that case/subject. Never accept code through URL, CLI argument, ticket field or login endpoint.

Gateway atomically consumes grant, inserts a 30-second pending-activation session with no data access and commits issuance audit using a SQLite transaction and conditional update with affected-row check. Bind technician ID, assignment revision, case, org, installation and target account. Database constraint prevents more than one session per grant. Concurrent losers receive generic grant_unavailable. Activation rechecks current local/Provider authority before making a pending session active. Failed/lost/expired activation and reissue retire pending reservations and release the account slot; the consumed code stays unusable. Reissue atomically revokes prior pending/active sessions for the account. Never return an old bearer credential to a retry.

Persistent attempt counters: five failures per verified technician/case-assignment-revision/installation challenge scope invalidate only that scope's outstanding grants, ten per technician/installation per 15 minutes, and 30 per installation per 15 minutes. Bound Provider source-IP requests too, using actual socket peer or explicitly trusted ingress, never arbitrary X-Forwarded-For. Wrong bindings cannot target another challenge scope's counter. Generic failures and capped parsing limit enumeration and cheap denial attacks. Implements R4–R7.

KTD5. Gateway is session authority, Provider is transport/actor authority

Use random 32-byte opaque browser session cookies, SHA-256 hashes at Provider, separate names and purpose from cp_session. Support cookie is __Host-prx_support, Secure/HttpOnly/SameSite=Strict/Path=/, without Domain. Provider cookie is __Host-prx_provider. Local customer browser never receives a support login credential. Session rows bind an opaque routing ID and actor/effective identity, not a customer password.

Before each support request, Provider authenticates the support cookie and linked technician session, introspects IdP token, checks authorization and builds a signed short-lived envelope. Envelope fields: protocol version, issuer/audience purpose, connection nonce, monotonically increasing sequence, random request ID, issued/expiry times, method, canonical relative target, body digest, technician ID/name, case/assignment revision, organization, installation and local session ID. Expiry at most 15 seconds and never beyond session expiry. Gateway checks signature/purpose, connection sequence, installation, local session, case, account current rights, expiry and revocation. Reject clock skew beyond 5 seconds. On restart or clock rollback, terminate support sessions and require new code.

Support auth takes precedence and fails closed: an invalid support context never retries password/tailnet auth even if such cookies were supplied. Revocation and expiry share a local authorization lock with request admission. Reads recheck immediately before releasing their bounded response. Mutations use the same admission lock, recheck authorization and persist intent audit before side effects. Revocation prevents later admission and cancels active requests/streams. Already committed effects and delivered bytes cannot be recalled. Implements R7, R9, R12.

KTD6. Optional outbound WebSocket connector, no loopback superuser

Both hosting models use the same optional connector so support has one tested route. Gateway initiates WSS to one configured broker. Reuse github.com/coder/websocket, already in go.mod. Provider registration uses a one-time 5-minute enrollment secret entered via protected stdin/file, binds a gateway-generated Ed25519 public key and writes a distinct 256-bit connector credential. Provider stores its hash. Customer explicitly pins Provider support-signing public key and broker hostname. Reconnect requires connector credential and proof of gateway private key over fresh challenge; broker proves the pinned support key. Rotate credentials/key under normal customer/Provider administration, never through support.

Broker never accepts a target URL from technician or request. It resolves installation ID to an enrolled connection. Connector dispatches parsed method/path/headers/body directly to an in-process support-only dashboard handler. It cannot dial loopback/network endpoints, spawn commands, tunnel CONNECT or reach gateway proxy, registry, OAuth callback or provider-admin handlers. No httputil.ReverseProxy pointed at an administrative listener using root credentials.

Versioned typed frames: challenge/proof, bounded case/assignment RPC, redemption, dashboard request/response, cancellation and heartbeat. Correlate request IDs, stream SSE in chunks with backpressure. Limit headers to 16 KiB, control JSON to 16 KiB, request bodies to 64 KiB, ordinary response to 4 MiB, SSE chunks to 64 KiB, eight dashboard requests per installation and one active support session per effective account. Header stripping rejects Authorization/Cookie/Forwarded/Tailscale/actor selectors and hop-by-hop headers. Preserve browser Origin only for validation, not identity.

Heartbeat every 10 seconds, connection timeout 30 seconds. A dropped or replaced connector closes all its sessions and pending grants, including at Provider and gateway. No automatic replay/resume or write retries. Local customer revocation remains usable during outage. Implements R6, R8, R11, R12.

KTD7. Dedicated support origin serves the real dashboard

Give each session an unguessable routing hostname under an operator-controlled wildcard, for example <session-id>.support.prx.nebuless.cloud. Host ID routes only and is not an authentication credential. Serve the gateway's own embedded assets, not Provider copies. Root-relative API URLs and hash routes keep working. No iframe, shared Domain cookie or localStorage token.

After redemption, Provider returns a no-store form POST to that origin's /__support/activate carrying a 30-second, single-use 256-bit handoff in the body. Provider verifies exact originating Provider origin, intended support host and linked technician session, consumes handoff and sets host-only support cookie. No token in redirect/query/fragment. Deny all activation GETs. Apply CSP frame-ancestors 'none', base-uri 'none', nosniff, strict referrer policy and HSTS on deployed HTTPS hosts. No credentialed cross-origin fetch or relaxed CORS.

Broker checks exact Origin/Host for state-changing browser requests before dispatch. Gateway support handler validates broker-asserted external origin against the registered session origin through a separate trusted transport context. Do not weaken csrfProtect globally or use authPublic to bypass it. Ordinary local CSRF/DNS-rebinding tests stay intact. Implements R3, R8, R9, R11.

KTD8. Explicit support capability ceiling and safe projections

Preserve the effective customer's ordinary permissions, including permitted non-secret mutations. Apply R8 security exclusions, not a blanket read-only role. Use current customer permissions and normal validation/confirmation flows. Support has no independent administrator authority.

Add method-aware SupportPolicy to webRoute, default denied. Explicit safe GET allowlist: dashboard assets, /api/state, /api/status, /api/profiles, /api/plugins, /api/rules, /api/analytics, /api/facets, summary-only /api/events and action-summary reads. Add GET /api/support/config-view for a typed allowlisted configuration projection. Allow ordinary account-authorized POST /api/agents/delete, POST /api/agents/profile and POST /api/actions/rule-preview with normal validators and confirmations. These cover current non-excluded mutations, not a weaker support role. Classify future routes against ordinary permissions and R8 before enabling support. Deny raw /api/config, action fixtures/bodies/downloads, credential/OAuth/Tailscale/onboarding/plugin-approval APIs, HITL decisions releasing proxy work, and arbitrary HCL config apply during support (ordinary customers retain configured dashboard_config_writes behavior) and all unclassified paths.

Support projections omit secret-slot defaults, literal HCL secrets, environment/file references, OAuth pending/authorization URLs, verification error strings, action headers/bodies, SQL arguments and webhook material. Use typed allowlisted DTOs from compiled state, never regex redaction of raw HCL. Apply the same data scope as effective-account ordinary reads, then redact. A profile query/header can narrow allowed context but cannot broaden it. Preserve account feature flags and normal allowed controls. Mark only R8 exclusions “Unavailable during support”. Ordinary config writes remain available when configured; support excludes arbitrary HCL apply because it can cross secret, routing and privilege boundaries. Never fake successful controls.

Bypass both gateway state cache/ETag and browser getState ETag cache during support. Send Cache-Control: no-store on all support responses/assets, disable service-worker caching if any is later added. Clear module state, unmount queries and close EventSource on 401/403/expiry/end/target change. Never let stale customer A data survive navigation to customer B. Implements R3, R8–R10.

KTD9. Dedicated synchronous security audit, not asynchronous request sink

Add gateway support_audit and Provider provider_audit. Every row has event/request ID, timestamp, actor ID/name/issuer, effective ID/name, org, installation, case, grant/session IDs, assignment revision, operation/route template/method, allow/deny, reason enum and outcome. Lifecycle attempts before subject resolution use nullable effective fields plus an explicit unresolved state. Do not fabricate a customer identity.

Commit an authorization/attempt row before dispatch or returning customer data. Read responses are bounded and buffered until outcome audit commits. Allowed SQLite mutations commit effects and outcome audit together after durable intent audit. Non-transactional effects need durable intent, operation ID, and success/failure or explicit unknown outcome on crash. Never retry automatically or claim audit failure undid a committed effect. A handler without a verified audit/side-effect boundary remains denied and blocks its required parity test until fixed. SSE commits opening audit and a fresh allow row before each bounded data delivery after local validity and Provider actor checks. If a completion audit fails, cancel/deny response and disable that support session. Use SQLite FULL synchronous commits for these security transactions, preserving the ordinary DB's existing WAL behavior elsewhere. Do not call Sink as the sole security log because it does not return an authorization commit acknowledgment.

Default audit retention 90 days, validated configurable range 30–365 days. Retain consumed/revoked grant/session metadata for that period without code HMAC after terminal state + 24 hours. Delete expired raw handoffs/provider sessions/access tokens within 24 hours and rate-limit buckets after 24 hours. Cases contain structured IDs and a maximum 240-character non-sensitive summary, not attachments or conversation text. Purge closed cases after audit retention. Customer inspects/exports local audit as paginated structured data. Provider retains metadata audit only, never customer response bodies. Backup retention must not exceed the approved retention window. Audit is local append-only application evidence, not a claim of tamper-proof storage against a host administrator. Implements R7, R10.

High-Level Technical Design

Deployment A runs customer gateway/client registry on customer infrastructure. Deployment B runs the same pair on Nebuless infrastructure in customer-specific state directories, OS service identities and network boundaries. Co-location never merges customer state directories, SQLite files, registry tokens or auth cookies. Provider registration contains no arbitrary upstream address to proxy.

Failure behavior and operational boundaries

  • Identity introspection failure, disabled technician, stale assignment or Provider authorization failure: deny support before gateway dispatch. Gateway also checks local support session on every accepted frame.
  • Gateway audit DB busy/full/read-only/corrupt: deny support results and terminate stream. Do not replace security evidence with console logging. Ordinary local dashboard retains its existing behavior and reports support unavailable.
  • Connector offline: no new case submission, grant issuance or redemption. Existing support closes. Customer can revoke locally and review prior audit. Customized registry continues from its own store and existing sync policy.
  • Reassignment, org/installation disable, account disable, password rotation or removal from current tailnet operator policy: invalidate related grants/sessions. Password reset hooks must revoke root's support sessions as well as its existing login sessions.
  • Unenrollment or key rotation: revoke all remote sessions, clear connector binding only after audited local authorization, retain audit. Never reuse revoked installation credentials.
