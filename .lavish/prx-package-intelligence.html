01 / Global knowledge

Aggregate once. Preserve sources.

Store advisory ranges, raw revisions, corrections and attribution for all four ecosystems. Serve enrolled PRX installations through authenticated endpoints.

Suggested starting point: one application, PostgreSQL and signed snapshot files. Capacity remains unmeasured.

02 / Local context

Keep each customer's environment local.

Store installed versions, graphs, private packages, policies and exceptions beside PRX. Synchronize advisories by package across versions, so tomorrow's disclosure is checked against today's inventory.

Public-name subscriptions reveal stack choices. Broader feed downloads reduce that disclosure at a bandwidth cost.

Two prevention boundaries

Before execution

A protected execution broker

A cached install can run without network traffic. PRX's network policy cannot inspect every local command.

Start with one pinned npm path, a reviewed lockfile, approved sources, scripts disabled and immutable graph/artifact authorization. The broker owns execution inside a controlled environment.

An optional check tool or PATH wrapper is advisory when the agent can bypass it. Python, Cargo and Go execution need their own acceptance work.

Before delivery

A protocol-aware response gate

Current PRX HTTP code forwards replies before usage analysis. Its WebSocket server-to-client path has no response rewrite gate.

Start with bounded, non-streaming JSON. Inspect complete structured calls and actionable package recommendations, then release or return a PRX policy error.

Streaming fragments require separate assembly and buffering. Already delivered bytes cannot be retracted. Unsupported transports must not quietly bypass strict mode.

What the code review actually established

cmd/nebprx/main.go:3294 calls resp.Write(tc) before usage analysis at line 3307. cmd/nebprx/ws.go:277 supplies no rewriter to the server-to-client pump. Credential transforms operate on outgoing requests. These are inspected code findings, not runtime prevention tests.

What “insecure” can and cannot mean

Known affected versions, malicious reports, missing names, untrusted sources and unresolved dependencies are distinct policy inputs. Full buffering fixes delivery timing, not every ambiguity in natural language. Do not block security discussion merely because it mentions a vulnerable version, or automatically replace it with “latest.”

Updates must carry evidence

Start with signed snapshots

Use TUF for signed, versioned and expiring delivery. Bind each bundle to its package scope. Verify it before atomic activation; retain the previous verified dataset on failure.

Later deltas must identify their exact base. Preserve withdrawals, explicit empty scopes, attribution and source health. A signature authenticates bytes; it does not prove advisory truth.

Make degraded operation visible

Known findings remain relevant during an outage. Stale negative results do not become current clearance. Withhold new admission when required intelligence or dependency evidence is missing.

Existing pinned operations may continue only under an explicit, bounded offline policy. Measure upstream checks, publication and client activation separately.

A prototype with observable gates

  1. Four-ecosystem intelligence. Validate identity, ranges, attribution, corrections and withdrawals against pinned reference tools.
  2. Two separate registries. Prove enrollment, scoped snapshots, first-seen packages, new disclosures, offline states and rollback rejection.
  3. One npm execution path. Demonstrate denial with a warm cache, immutable authorization and blocked bypass routes.
  4. One non-streaming response adapter. Demonstrate zero denied content delivered, valid error handling and bounded malformed-response behavior.
  5. Expand by tested capability. Add Python, Cargo, Go, streaming and more agents through separate acceptance suites.

The enforcement report defines 27 adversarial acceptance cases. They are proposed tests, not passing results.

Decisions to carry into implementation

Choose the first managed client/agent versions, acceptable response buffering, offline continuity rules and whether public package names may leave the customer. Establish measured freshness and capacity targets after the prototype.

Defensible eventual claim: PRX blocks policy-disallowed known package/version findings on supported, enforced execution and response paths.

Connect the assessment to the controls

The on-site assessment can establish which agents, execution tools, package sources and dependency inventories exist; who owns approvals; and which workflows need offline continuity. Those findings determine the first enforceable PRX paths and the customer's local registry scope.
